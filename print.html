Relift Documentation

Relift Documentation

Welcome to the Relift documentation. Relift is a free, open-source, read-only deleted-file recovery tool for disk images and drives.

Preview status. Validation is limited to deterministic synthetic fixtures. No physical drive or representative recovery corpus has been validated. Release binaries are unsigned. See Verification for the current evidence boundary.

What Relift Does

Relift scans disk images and raw devices without writing to them, records what it finds in a session directory, and recovers validated byte ranges only to a separate destination. Unsupported filesystems and unvalidated carves are reported, never silently presented as recovered.

Key Features

  • Read-only by construction – ReadOnlySource exposes no write method; the engine cannot modify the source device
  • Byte-for-byte recovery verified against synthetic fixtures with SHA-256
  • Filesystem metadata recovery – FAT12/16/32, exFAT, NTFS, ext2/3/4 (fixture-validated); HFS+, APFS, Btrfs and XFS parsers are implemented but experimental
  • Signature carving – 36 structurally validated formats, including JPEG, PNG, PDF, ZIP, MP4, MP3, SQLite, FLAC, RAR5, OLE, MPEG-TS, and ISO 9660 (full list in Supported Formats)
  • Session-based workflow – scan → session → recover → report, with checkpoint resume
  • Cross-platform – Windows, macOS, and Linux
  • No telemetry – fully offline by default

Installation

From Source (Rust)

Requires Rust 1.90 or newer. On Windows, the MSVC toolchain is recommended:

rustup default stable-x86_64-pc-windows-msvc
cargo build --release --workspace

The CLI binary is target/release/relift.exe (Windows) or target/release/relift (Unix).

Desktop GUI (Tauri)

The GUI requires Node.js 22.17 or newer:

cd crates/relift-gui
npm ci
npm run tauri build

This produces Windows MSI and NSIS installers in target/release/bundle/.

Prebuilt Binaries

Prebuilt binaries are available on the Releases page. The v0.1.0 preview includes:

  • Windows: MSI and NSIS installers (x86_64)
  • macOS: x86_64 and arm64 bundles
  • Linux: x86_64 and ARM64 CLI archives
  • SHA256SUMS manifest for all assets

All preview assets are unsigned; hashes detect byte mismatches but do not authenticate the publisher.

Package Managers

Package-manager manifests (Homebrew, winget, Scoop, AUR, Flatpak, Snap) are templates and have not yet been submitted to upstream repositories.

Quick Start

Scan a Disk Image

  1. Image a raw device (recommended over scanning a mounted volume):
relift image \\.\PhysicalDrive1 --dest D:\images\evidence.dd
  1. Scan the image:
relift scan D:\images\evidence.dd --session D:\session --live --carve
  1. Recover deleted files to a separate destination:
relift recover D:\session --dest D:\recovered

Continue an Interrupted Scan

If a scan was interrupted, resume it (the source must be unchanged):

relift scan image.dd --session ./session --resume

List Devices

relift devices

Run Self-Tests

relift doctor

Commands

relift devices

List physical disks and partitions exposed by the operating system.

relift devices [--json]

relift scan

Probe filesystems and write deleted-file candidates to a session directory.

relift scan <SOURCE> --session <DIR> [OPTIONS]
OptionDescription
<SOURCE>Disk image path or raw device (e.g., image.dd, \\.\PhysicalDrive1)
--session <DIR>New or empty directory for session output; an existing interrupted session with --resume (required)
--resumeContinue an interrupted session. Uses the session's recorded options and requires an unchanged source
--mode <MODE>Scan preset: quick (metadata only) or deep (metadata + validating carving) (default: quick)
--liveAlso list files that are still allocated
--carveRun signature carving in addition to metadata recovery (implied by --mode deep)
--volume <INDEX>Scan only this volume index (repeatable)
--offset <BYTES>Manual volume offset in bytes (requires --length)
--length <BYTES>Manual volume length in bytes (requires --offset)
--max-candidates <N>Stop after this many candidates (default: 1,000,000)
--jsonMachine-readable JSON output

Examples:

# Quick metadata scan (never reads the whole volume)
relift scan /dev/sdb --session ./session

# Deep scan with validating signature carving
relift scan image.dd --session ./session --mode deep

# Continue a cancelled or crashed scan (the source must be unchanged)
relift scan image.dd --session ./session --resume

# Scan only a specific volume index
relift scan /dev/sdb --session ./session --volume 2

# Manual volume range
relift scan image.dd --session ./session --offset 1048576 --length 1000000000

Resume semantics. The checkpoint advances only after a whole volume has been scanned and its candidates have been flushed to disk. --resume skips volumes already recorded as complete and rescans the interrupted volume from its start; candidates written after the last completed volume are discarded. The session's recorded options (carving, live entries, volume selection, manual range, candidate limit) are reused. The source is re-opened read-only and its size and sampled fingerprint must match the session, otherwise resume is refused with exit code 4. Live pause/resume is not supported, and imaging has no resumable map-file workflow.

relift list

List candidates saved in a session without writing anything.

relift list <SESSION> [OPTIONS]
OptionDescription
<SESSION>Session directory produced by relift scan
--filter <EXPR>Filter candidates (repeatable): ext:jpg,png, format:pdf, name:IMG_, path:DCIM
--min-confidence <LABEL>Hide candidates below this confidence (verified, likely, partial, unverified)
--limit <N>Maximum rows to print (0 means all) (default: 100)
--jsonMachine-readable JSON output

Filter expressions:

ext:jpg,png,mp4          # by file extension or filename extension
format:pdf               # by recorded candidate format
name:IMG_                # case-insensitive filename substring
path:DCIM                # case-insensitive path substring

Multiple --filter expressions are ANDed; comma-separated values within one expression are ORed.

Examples:

# List all candidates (first 100)
relift list ./session

# Only verified JPEGs and PNGs
relift list ./session --filter 'ext:jpg,png' --min-confidence verified

# JSON output
relift list ./session --json

relift recover

Recover candidates from a session into a destination directory. The source's identity must still match the session record; a changed image is refused.

relift recover <SESSION> --dest <DIR> [OPTIONS]
OptionDescription
<SESSION>Session directory produced by relift scan
--dest <DIR>Destination directory (must be on a different physical device)
--source <PATH>Re-open this source instead of the path recorded in the session
--filter <EXPR>Filter candidates (repeatable): same expressions as relift list
--dry-runPlan only: validate source and destination, list what would be written. No files are written and the session is not modified.
--no-verifyDo not re-read each output file after writing it (verification is on by default)
--min-confidence <LABEL>Skip candidates below this confidence (verified, likely, partial, unverified)
--id <N>Recover only these candidate IDs (repeatable)
--jsonMachine-readable JSON output

Examples:

# Recover all candidates
relift recover ./session --dest /mnt/recovery

# Only verified JPEGs, dry run first
relift recover ./session --dest /mnt/recovery --filter 'ext:jpg' --min-confidence verified --dry-run

# Recover specific IDs only
relift recover ./session --dest /mnt/recovery --id 123 --id 456

# Without post-write hash verification
relift recover ./session --dest /mnt/recovery --no-verify

Desktop GUI

Relift's desktop interface uses Tauri 2 and Svelte 5. It calls the shared relift-core library through Tauri commands. The GUI is a subset of the CLI; see CLI.md for imaging, report export, shell completions, and other commands.

Choose a source

The first screen lists devices visible to the operating system and lets the user select a raw image file. It shows the device path, type, size, filesystem label when available, accessibility status, and any OS-provided note. It does not inspect SMART health or reliably determine SSD TRIM status. Only raw image files are supported directly.

The safety notice recommends stopping use of the source and recovering to a different physical drive. If the source is failing, consider professional recovery or image it before scanning.

Advanced options currently include:

  • Quick scan: filesystem metadata.
  • Deep scan: metadata plus validated signature carving.
  • Include files that are still allocated.

Formatted-partition recovery, lost-partition recovery, and worker-thread controls are not implemented.

Scan

The scan screen receives progress events from the running scan and displays phase, bytes processed, elapsed time, estimated throughput, ETA, and the number of candidates saved in the session. ETA and throughput are estimates, not promises. The user can stop the scan and keep results already written to the session. Live pause is not implemented, and the GUI does not expose the CLI's checkpoint-resume workflow.

Candidates are reviewed after the scan finishes or is stopped. The GUI does not preview or recover candidates while scanning.

Review and recover

The results screen supports text search, type and confidence filters, sorting, selecting visible rows, and selecting Verified/Likely candidates. Its preview shows candidate metadata and validator notes; it does not render the recovered file contents.

The user selects a destination folder and starts recovery. The shared recovery engine validates the destination and verifies output hashes by default. The GUI shows recovered, partial, failed, and byte counts when the operation finishes. Recovery destination safety is still subject to the platform limits in support-matrix.md.

Current exclusions

  • No imaging workflow in the GUI; use relift image from the CLI.
  • No report format picker in the GUI; use relift report from the CLI.
  • No content viewer, folder-tree view, or 500,000-row performance claim.
  • No pause/resume for a running scan, and no resume control in the GUI; the backend supports relift scan --resume from the CLI.
  • No device-health, SMART, or TRIM diagnosis.
  • No real screenshot evidence is included in the repository yet. See GUI_CAPTURE.md for the owner-run capture procedure using deterministic synthetic fixtures.

The GUI is built in the release workflow, but platform runtime behavior, accessibility, cold-start time, and large-result performance have not been measured as release gates. See VERIFICATION.md.

Filesystem support reference

This document summarizes what the current parsers implement. The status and test evidence are in the support matrix. A parser being present does not establish recovery accuracy on a real volume.

Fixture-tested parsers

FAT12, FAT16, FAT32

The parser reads directory entries, long file names, and cluster chains. Deleted data may be incomplete when allocation metadata has been cleared or clusters have been reused. The short-name deletion marker loses its first byte.

exFAT

The parser reads directory entry sets and uses allocation metadata and the NoFatChain flag. Recovery can be incomplete when the expected FAT chain is unavailable or the file data has been overwritten.

NTFS

The parser reads MFT records, resident and non-resident unnamed data, runlists, and sparse runs. It does not follow ATTRIBUTE_LIST continuation records, recover named alternate data streams, decompress LZNT1, decrypt EFS, replay the USN journal or LogFile, or parse Recycle Bin metadata as a separate source.

ext2, ext3, ext4

The parser reads inode metadata, supported block/extent mappings, directory entries, sparse extents, and unwritten extents. It does not replay the journal, recover inline data larger than 60 bytes, decrypt fscrypt data, or support bigalloc. Deletion and reuse can remove the metadata needed to locate content.

Experimental parsers

HFS+, APFS, Btrfs, and XFS parsers are wired into scanning. Deterministic probe fixtures and end-to-end detection tests exist (probe_identifies_hfsplus, probe_identifies_apfs, probe_identifies_btrfs, probe_identifies_xfs), but metadata-based deleted-file recovery has not been validated against a fixture or real volume. Treat recovery results as experimental. Snapshot enumeration, encryption, compression, hardlink resolution, and other filesystem-specific cases are incomplete; see limitations.

Detection without metadata recovery

ReFS, F2FS, ZFS, ReiserFS, ISO 9660, and UDF may be identified by probing, but metadata recovery is not implemented.

Scan mode

Quick mode scans supported filesystem metadata. Deep mode also runs the registered signature validators. Formatted-volume and lost-partition scan modes are not implemented. See docs/CLI.md for exact options.

Evidence boundary

Current metadata recovery evidence is from deterministic synthetic FAT32, exFAT, NTFS, and ext4 fixtures. No real physical volume or representative real-media corpus has been validated. For details, use the support matrix, limitations, and gap report.

Carved Format Reference

Relift searches for registered signatures and emits a candidate only when the corresponding validator accepts the structure. A candidate passing validation is evidence about its container structure; it is not proof that the file is complete, uncorrupted, or openable in every application.

The implementation is in crates/relift-core/src/carve.rs. The 153 formats below are registered for carving; a format without a working validator is not emitted.

Not emitted

  • ZIP64: shares the PK\x03\x04 local-header magic with ZIP and is handled by the existing ZIP validator. A dedicated ZIP64 end-of-central-directory validator is not implemented.

See support-matrix.md and GAP_REPORT.md for the current support boundary.

Validation limits

Validators enforce format-specific length, structure, checksum, and/or end marker rules where implemented. Validation depth differs by format and is not a substitute for a format library or application-level verification. Embedded compressed or encrypted content is recovered as bytes; Relift does not decrypt or extract it.

The confidence labels are evidence categories, not probabilities. A validated fragment may still be incomplete because the source file was fragmented, overwritten, or truncated. Recovery SHA-256 verification checks that the bytes written to the destination match the bytes read back; it does not prove they match an original copy.

Adding a format

Follow the contribution guide and add valid, truncated, and malformed test fixtures before registering a new marker. Do not emit a format based only on a magic-byte match. The registered_format_count_is_stable unit test fails when the marker set changes, which is the prompt to update this page and the support matrix.

Forensic Use and Evidence Handling

Relift is a data-recovery utility, not a certified forensic acquisition tool. It has no case-management mode, DFXML export, source-range hashing, investigator fields, hardware write-blocker control, or forensic-grade checkpointing. Scan resume is a crash-recovery convenience, not a chain-of-custody control. Do not describe its output as a validated forensic image or a complete chain-of- custody record.

For legally or professionally consequential evidence, follow your organization's procedures and applicable standards. Use a hardware write blocker and a validated forensic acquisition tool when required. Have a qualified examiner review the acquisition and analysis plan.

Safer recovery workflow

  1. Stop using the source device. Do not write recovered output back to it.
  2. Confirm the source and destination with the operator. The destination must be a different physical volume.
  3. If appropriate, create a raw image on the separate destination. Relift's image command makes a single-pass copy and writes a SHA-256 manifest; it does not provide bad-sector maps, retries, or multi-pass resume.
  4. Scan the image, review candidates, and run a dry-run recovery.
  5. Recover only after confirming the dry-run and destination. Keep the image, session directory, report, and recovered output under controlled storage.

Example for an already-created raw image:

relift scan /evidence/source.img --session /evidence/session --mode quick
relift list /evidence/session --json
relift recover /evidence/session --dest /recovery --dry-run
# After reviewing the plan and confirming /recovery is a separate physical volume:
relift recover /evidence/session --dest /recovery
relift report /evidence/session --format json --out /evidence/report.json

For metadata plus carving, use --mode deep. Raw device paths, permissions, and destination checks vary by operating system; see support-matrix.md.

What the session records

The session directory stores a versioned JSON header, candidate JSONL records, recovery-result JSONL records, and a README. The source identity uses a fingerprint derived from source size and sampled bytes; it is not a cryptographic hash of every source byte. Recovered output files are SHA-256 verified by default after writing. The image manifest contains the image copy's hash.

These records are useful for repeatable recovery work, but are not a tamper-proof audit log and do not replace independent evidence acquisition, full-source hashing, timestamps from a trusted clock, or examiner notes. Preserve copies and compute any hashes required by your procedure independently.

Important limits

  • The source abstraction is read-only, but this alone does not certify forensic soundness or prevent the operating system from changing a mounted source.
  • Destination separation is checked by Relift where the platform can establish physical backing. Review warnings and do not use an ambiguous destination.
  • Only raw disk images are supported directly; other containers must be converted with an appropriate tool.
  • Filesystem recovery has deterministic synthetic-fixture evidence only. Real-media accuracy and forensic validation have not been established.
  • Relift does not decrypt BitLocker, LUKS, or FileVault, reconstruct RAID, or repair partition tables.
  • No --forensic, --case-id, --investigator, --verify, or DFXML export option exists. SHA-256 recovery verification is on by default and can be disabled with --no-verify.

See limitations.md, GAP_REPORT.md, and VERIFICATION.md for current support and evidence status.

Troubleshooting

Use the command reference in CLI.md for available flags. Relift does not implement --max-mem, --threads, --rate-limit, image map files, or a forensic mode. Scan resume is available as scan --resume; it is not a live pause control.

Device access

  • Raw-device access may require Administrator on Windows or elevated permissions on Linux and macOS.
  • Prefer a raw image when possible. Only raw image files are supported; convert E01/AFF4/VHD/VMDK/QCOW2/DMG containers before scanning.
  • relift devices lists devices visible to the operating system.
  • relift doctor runs local self-tests and also attempts a read-only open and a 512-byte read from a platform-specific raw-device path. Confirm with the device owner before running it on a system with physical media attached.

Scan problems

The scan finds no candidates

Run a quick metadata scan first. If it finds nothing and the filesystem or source is suitable, a deep scan also runs the supported signature validators:

relift scan image.dd --session ./session --mode quick
relift scan image.dd --session ./deep-session --mode deep

Deleted content may already have been overwritten or erased by SSD TRIM. A full overwrite cannot be reversed. Encrypted volumes are not decrypted by Relift.

The session directory is not empty

Use a new or empty directory for --session. A scan does not overwrite an existing session's files.

The scan is interrupted

Candidates already written to the session are retained. Continue the same session with relift scan <source> --session <dir> --resume; the source must be unchanged. Resume skips volumes already completed and rescans the interrupted volume from its start, discarding candidates written after the last completed volume. The GUI's stop action cancels scanning and keeps the results already recorded; it has no resume control.

The source changes before recovery

Relift compares source size and fingerprint with the session. If they differ, re-scan the current image into a new session. The --source option can select the intended source path, but does not bypass the identity check.

Recovery problems

The destination is rejected

Choose a directory on a different physical volume. Some virtual, stacked, or multi-device destinations are refused when Relift cannot prove their physical backing. Use an ordinary local volume or a raw image as the source.

Run recovery with --dry-run first. Confirm the destination is a separate physical volume before writing.

A recovered file is partial or will not open

Content can be incomplete if the original file was fragmented, overwritten, truncated, or only partially validated. Confidence labels describe the available recovery evidence; they are not probabilities or guarantees that an application can open the file. SHA-256 verification checks that output bytes were written consistently, not that they match an unavailable original.

Recovery stops with an error

Inspect the JSON or human-readable recovery summary and run relift report <SESSION> --format json. Linux and macOS may retain a failed output under a collision-safe .partial name; Windows removes failed output.

Imaging problems

relift image creates a new raw image and refuses to overwrite an existing destination. It performs a single-pass copy; it does not retry bad sectors or resume from a map file. For a failing or physically damaged drive, stop using it and consider professional recovery or a dedicated imaging tool designed for read errors.

GUI problems

The GUI requires the platform's Tauri webview runtime and the native build dependencies listed by Tauri. On Windows, install WebView2 if it is missing. On Linux, install WebKitGTK and the system dependencies required by the distribution. Release bundles are unsigned and may produce operating-system warnings.

Still stuck?

Check GAP_REPORT.md, limitations.md, and the current GitHub issues. Include Relift version, OS, filesystem, source type (image or device), command, and relevant warning/error output. Do not attach images or recovered files that contain private data.

Architecture

Relift is a Rust workspace with one shared recovery library, a native CLI, a Tauri desktop application, deterministic test fixtures, and a Criterion benchmark crate. The CLI and GUI call the same relift-core APIs.

Data flow

flowchart LR
    A[Image or raw device] --> B[Read-only source]
    B --> C[Partition and filesystem probes]
    C --> D[Metadata scan]
    C --> E[Validated carving when requested]
    D --> F[Candidate session]
    E --> F
    F --> G[CLI or GUI review]
    G --> H[Destination validation]
    H --> I[Recovery writer]
    I --> J[Output hash verification]
    B --> K[Imaging command]
    K --> L[New raw image and manifest]

Source and scan path

ReadOnlySource provides positional reads and identity information but has no write operation. The CLI and GUI open regular image files or platform raw devices through this abstraction. Raw-device access and physical-disk identification have platform-specific limits described in support-matrix.md.

The scanner probes partitions and supported filesystems. Quick mode scans metadata; deep mode also runs the signature validators. Metadata and carve results become Candidate records with source locations, extents, recovery method, and confidence. Experimental parsers are listed separately from fixture-validated filesystems.

Session format

A session is a directory, not a database:

  • session.json stores schema version, source identity, scan options, summary, filesystem reports, warnings, and recovery totals.
  • candidates.jsonl stores one candidate per line and is appended as results are produced.
  • recovered.jsonl records recovery results.
  • README.txt describes the session.

Candidate records stream to disk rather than being accumulated into one in-memory result list. A completed session can be listed, recovered, or reported again. session.json also stores a volume-level checkpoint: after a volume's metadata and carving work is flushed and synced, the checkpoint records the volume index and the durable length of candidates.jsonl. relift scan --resume truncates back to that boundary, rebuilds the summary from the surviving records, and continues. The interrupted volume is rescanned from its start; there is no chunk-level checkpoint.

Recovery and imaging writes

The recovery path opens and validates the source, compares its identity with the session, validates the destination, then writes only under the selected destination directory. Destination handling uses anchored directory handles, no-follow path traversal, and collision-safe file creation/finalization. On supported platforms, same-device destinations are rejected; cases whose physical backing cannot be proven fail closed. Platform details and remaining limits are in GAP_REPORT.md.

Recovered files are re-read and SHA-256 checked by default. --no-verify disables this post-write check. The image command copies from a read-only source to a new raw image destination and writes a SHA-256 manifest; it does not overwrite an existing destination.

Interfaces

The CLI exposes the complete current command set and machine-readable JSON. The GUI covers source selection, scanning, result review, preview, and recovery. Imaging, report-format selection, and checkpoint resume remain CLI-only. The GUI can stop a scan and keep partial results; it does not pause a running scan. See CLI.md and GUI.md for user-facing behavior.

Verification boundaries

Tests prove behavior on deterministic synthetic fixtures, including byte-level recovery comparisons and destination safety cases. CI builds and tests the workspace on Windows, macOS, and Linux. No real physical disk or real deleted volume has been validated yet; no accuracy percentage or hardware performance target is claimed. See VERIFICATION.md.

Threat Model

Scope and assumptions

Relift reads disk images and raw devices that may contain corrupt or hostile metadata. It writes recovered files or images only under a user-selected destination. The source, session, command-line paths, and file contents are untrusted inputs. Relift is not a certified forensic tool and does not defend against a compromised operating system or a local process that controls the destination volume.

Assets

  1. Source integrity: scanning and imaging must not write to the source.
  2. Destination confinement: recovered paths must remain inside the chosen destination and must not overwrite an existing file unexpectedly.
  3. Recovered-data integrity: report successful output verification and distinguish partial or failed recovery.
  4. User privacy: do not send device data, file contents, or telemetry over the network.
  5. Process stability: reject malformed offsets and structures safely and avoid unbounded result accumulation where the session writer can stream data.

Controls implemented

Source and destination

  • The core scanner accepts a ReadOnlySource with no write operation.
  • Imaging and recovery use explicit destination writers. Destination paths are opened component-by-component, without following links, and retained as handles while output is created. Output files use collision-safe creation.
  • Source identity is recorded in the session; recovery refuses a source whose size or fingerprint differs from the recorded source.
  • Platform-specific physical-device checks reject known same-device recovery destinations. When backing cannot be proven, supported paths fail closed.
  • Recovered output is SHA-256 checked by default. The user can disable the post-write read-back check with --no-verify.

Parser and output handling

  • Parsers use bounded reads and checked range validation at input boundaries.
  • Signature carving emits a candidate only when its format validator accepts the structure.
  • Filesystem and carve limitations are recorded in the support matrix and gap report; a signature match alone is not represented as validated recovery.
  • Candidate records stream to JSONL session files rather than being retained as one in-memory result set. --max-candidates limits the number of candidates.
  • Recovered names are sanitized and destination traversal is rejected. See GAP_REPORT.md for platform-specific output behavior.

Privacy and dependencies

  • The core and CLI contain no network client or telemetry.
  • The doctor command reports network/telemetry status but also attempts a read-only open and 512-byte read from a platform-specific raw-device path.
  • cargo deny check runs in CI for dependency advisories, licenses, bans, and source configuration.

Remaining threats and evidence gaps

  • Synthetic tests do not prove safety against every malformed image or real device behavior. No comprehensive fuzz harness or 24-hour fuzz campaign is checked in.
  • The Linux device-ancestry tests are synthetic; there has been no same-device refusal test against mounted physical disks.
  • Raw-device behavior and physical destination checks are not validated on actual media. macOS raw-device access is untested and destination checks fail closed.
  • Resource behavior on multi-terabyte images and very large candidate sets has not been profiled. There is no --max-mem or --timeout option.
  • Scan resume is volume-level: an interrupted volume is rescanned from its start, and candidates written after the last completed volume are discarded. The source fingerprint samples head/tail bytes rather than hashing the whole source, so a change outside the sampled ranges is not detected. A process crash may leave partial destination output; failed-output cleanup differs by platform.
  • A local process with write access to the destination can alter output or cause denial of service.
  • No signed release artifacts or notarized GUI bundles exist. The published v0.1.0 preview has unsigned assets; its SHA256SUMS file does not authenticate the publisher.

Forensic limits

Relift is a recovery utility, not an evidence-acquisition or chain-of-custody system. Session fingerprints sample the source rather than hashing every byte; session files are not tamper-evident. No case-management mode, DFXML export, or source-range hashing is implemented. For forensic use, follow organizational procedures, use an appropriate write blocker, and independently acquire and hash evidence with validated tools.

See VERIFICATION.md for test results and release gates.

Known Limitations

This document lists current, verified limitations. It intentionally avoids claiming features that are not implemented. See docs/GAP_REPORT.md for the tracked work list.

Filesystem parsing

NTFS

  • $ATTRIBUTE_LIST is not followed; only the base record's unnamed $DATA (resident or non-resident) is recovered.
  • Named alternate data streams are not recovered.
  • LZNT1 compression and EFS encryption are reported, not decoded.
  • $LogFile and $UsnJrnl are not replayed.
  • Hardlinks/reparse points are not resolved; only the first known name is used.
  • $I30 index slack and $Recycle.Bin are not parsed as separate sources.

FAT12/16/32

  • A quick format zeroes the FAT; cluster chains are lost. Deleted files are assumed contiguous, which can truncate or over-extend output.
  • The 0xE5 delete marker destroys the first short-name byte. LFN is used when available; otherwise the missing byte becomes _.
  • Corrupt LFN checksums do not invalidate the decoded name; the checksum is treated as informational.

exFAT

  • NoFatChain is handled; when a FAT chain is expected but zeroed, recovery falls back to contiguous allocation and may be incomplete.
  • The allocation bitmap is used for probing, not as a complete free-space map.

ext2/3/4

  • Deletion commonly zeroes extent/block pointers. Recovery uses surviving inode fields, directory entries and contiguous-run heuristics.
  • Inline data larger than the inode body (>60 bytes) is not recovered.
  • fscrypt-encrypted inodes are reported as unverified, not decrypted.
  • bigalloc is refused as unsupported.
  • Journal replay is not performed.

HFS+, APFS, Btrfs, XFS

  • Parsers are implemented and probe fixtures exist, but metadata-based deleted-file recovery has no deterministic end-to-end test yet.
  • APFS/Btrfs snapshot trees are not enumerated as separate recovery sources.
  • APFS clone extents and FileVault-encrypted volumes are not decoded.
  • HFS+ journal replay and hardlink/alias resolution are not implemented.
  • Btrfs compressed extents (zstd/lzo) are not decompressed.
  • XFS inode numbers from B+tree leaves are approximate.

ReFS / F2FS / ZFS / ReiserFS / ISO 9660 / UDF

  • Detection only. Metadata recovery is not implemented; raw carving may still find content on the underlying bytes.

Carving

Formats without a dedicated validator

  • ZIP64: shares the PK\x03\x04 local-header magic with ZIP and is validated by the existing ZIP validator rather than a separate carver. A dedicated ZIP64 end-of-central-directory validator is not yet implemented.

Every other registered format carries its own structural validator, and an unvalidated carve is never emitted.

Fragmentation

  • Bifragment gap carving is not implemented for most formats.
  • Fragmented MP4/MOV (moof/mdat) chains are not reassembled.
  • JPEG recovery after a large non-JPEG gap is heuristic and may truncate or over-extend.

Limits

Per-format size caps are enforced by each validator; files exceeding the cap are not carved. See the constants in crates/relift-core/src/carve.rs.

Platform

Windows

  • Raw physical disk access requires administrator elevation.
  • Non-elevated runs list drive letters only and warn.
  • GUI requires the WebView2 runtime (included in Windows 10 1809+).

macOS

  • Raw-device destination safety fails closed; imaging is recommended.
  • Full Disk Access is required for raw devices.
  • Raw-device paths have not been exercised in this repository.
  • No signing/notarization: Gatekeeper warnings are expected.

Linux

  • Raw block devices normally require root.
  • No io_uring or O_DIRECT path; reads use ordinary positioned file I/O.
  • LVM/RAID reconstruction is not implemented.

Recovery

Destination safety

  • A destination on the same physical device as the source is refused.
  • Network and FUSE destinations are allowed but atomicity is not guaranteed.

Verification

  • SHA-256 is computed by default; --no-verify disables the re-read check.
  • Failed-output handling differs by platform: Windows removes a failed output; Linux and macOS retain a collision-safe .partial file when possible.
  • Sparse holes are written as zeroes and included in the hash.

Sessions

  • Sessions are directories with session.json, candidates.jsonl, and recovered.jsonl; they do not use SQLite.
  • Completed sessions can be listed, recovered, and reported later. A cancelled or crashed scan can be continued with relift scan --resume; the checkpoint is volume-level, so the interrupted volume is rescanned from its start.
  • Recovery refuses a source whose size or fingerprint no longer matches the identity recorded in the session. Scan resume applies the same check.

Performance

  • No published benchmark results exist yet. Run cargo bench -p relift-bench on your hardware and record the environment described in docs/benches/METHODOLOGY.md.
  • Carving is single-pass and bounded-memory; very large images are processed incrementally rather than mapped whole.

Recovery Tool Comparison

Relift has not been evaluated in a reproducible, head-to-head recovery study. The repository contains deterministic synthetic fixtures, not a representative corpus of deleted files or measurements against other products. This page therefore does not rank recovery tools or claim that Relift is faster, more accurate, safer in practice, or more complete than another product.

What has evidence in this repository

  • FAT12/16/32, exFAT, NTFS, and ext2/3/4 have synthetic fixture tests.
  • HFS+, APFS, Btrfs, and XFS are experimental and lack fixture validation.
  • Carved candidates are emitted only after a format-specific validator accepts them; that does not establish recovery accuracy on real-world data.
  • Recovery and imaging write to a validated destination path; raw-device behavior has not been tested against physical disks.
  • The CLI can export JSON, HTML, and CSV reports. The GUI covers a subset of CLI capabilities.

See support-matrix.md and VERIFICATION.md for the evidence and gaps.

How to compare tools for a recovery case

Compare the exact filesystem, deletion/format scenario, image format, and platform you need. Use a disposable test image with known file contents, record which files each tool restores byte-for-byte, and publish the test image, commands, tool versions, and system profile. Do not compare headline format counts or scan speed unless the inputs and validation rules are equivalent.

For a failing or irreplaceable drive, stop using it and consider a professional recovery service. Relift is not certified for forensic evidence acquisition, partition repair, RAID reconstruction, or encrypted-volume recovery.

Frequently Asked Questions

Recovery and safety

What does Relift do?

Relift scans raw disk images and raw devices for recoverable filesystem metadata and structurally validated file signatures. It stores findings in a session directory, then can write selected files to a separate destination. The main workflows are documented in CLI.md.

Which filesystems are supported?

FAT12/16/32, exFAT, NTFS, and ext2/3/4 have deterministic synthetic fixture coverage. HFS+, APFS, Btrfs, and XFS parsers are experimental and have not been validated against fixtures or real volumes. See the support matrix.

What file types can it carve?

Relift emits only formats with structural validators. The current list and known omissions are in support-matrix.md. A recognized signature alone is not enough to emit a candidate.

Does Relift write to the source?

Scanning uses a read-only source interface. Recovery and imaging write to separate destination paths. Always confirm that the destination is on a different physical volume, and run recovery with --dry-run first. Do not let an agent access a physical device without first confirming the source and destination with a human.

Can I recover deleted data from an SSD?

Sometimes, if the content has not been erased or overwritten. TRIM and garbage collection often make deleted SSD content unrecoverable. Relift does not determine that data is recoverable just because metadata remains.

What happens after a format or overwrite?

If sectors were overwritten or discarded, their previous bytes cannot be recovered by software. A quick format may leave some metadata or content; a full overwrite generally does not.

Does Relift support encryption or RAID reconstruction?

No. Relift does not crack or bypass encryption and does not reconstruct RAID, LVM, or other multi-device volumes. Decrypt or assemble the source with authorized tools first, then provide a supported raw image or device.

Can it read E01, VHD, VMDK, QCOW2, or DMG images?

No. Convert those containers to a raw image before scanning. Only raw images are supported directly.

How do I handle a failing drive?

Stop using it. If it is clicking, beeping, disconnecting, or returning repeated read errors, consider professional recovery. Relift's image command makes a single-pass raw copy; it does not provide ddrescue-style maps, retries, or multi-pass resume. Image to a different physical volume before scanning when the device is stable enough to read.

Can I pause or resume a scan?

Relift cannot pause a running scan. If a scan is cancelled or the process crashes, relift scan <source> --session <dir> --resume continues it after revalidating the source. Completed volumes are skipped and the interrupted volume is rescanned from its start, so that volume's candidates are regenerated rather than duplicated. The GUI can stop a scan but does not expose resume.

Using Relift

How do I start with an image?

relift scan image.dd --session ./session --mode quick
relift list ./session
relift recover ./session --dest /mnt/recovery --dry-run

Review the dry-run output, confirm the destination is on a separate physical volume, then run recovery without --dry-run.

How do I scan for carved files?

relift scan image.dd --session ./session --mode deep

Deep mode includes metadata scanning and validated signature carving. Carved files may be partial, especially when the original file was fragmented or overwritten.

How do I select files to recover?

Use candidate IDs, extensions, confidence labels, or path/name filters. For example:

relift recover ./session --dest /mnt/recovery \
  --filter 'ext:jpg,png,pdf' --min-confidence likely --dry-run

The complete filter grammar is in CLI.md. Confidence labels are evidence categories, not probabilities or guarantees that an application can open the file.

Does Relift verify recovered files?

Yes. Recovery re-reads and SHA-256 checks output files by default. The --no-verify option disables that check. Relift does not verify files by comparing them with an original copy unless you supply that comparison separately.

What is a session directory?

A session is a directory containing session.json, candidates.jsonl, recovered.jsonl, and a short README. It is not a SQLite database. Session fields are versioned; see CLI.md and the implementation overview in architecture.md.

What does relift doctor check?

It runs local storage, hashing, and carving self-tests, checks telemetry/network status, and attempts a read-only open and 512-byte read from a platform-specific raw-device path. It may therefore access a physical device; do not run it on behalf of someone else without confirming first.

Interfaces and distribution

Is there a GUI?

Yes. The desktop app uses Tauri 2 and Svelte 5. It covers source selection, scanning, result review, preview, and recovery. Imaging and report format selection are currently CLI-only. See GUI.md.

Is there a TUI or self-update command?

No. The supported interfaces are the CLI and desktop GUI. relift self-update is not implemented.

Does Relift send files or telemetry over the network?

The core and CLI have no network client or telemetry. No account or cloud service is required.

Is there a stable release or package-manager installer?

The v0.1.0 preview is published with unsigned assets and a SHA256SUMS file. No stable, signed, or notarized release is available. Homebrew, winget, Scoop, AUR, Flatpak, and Snap submissions have not been completed. See GAP_REPORT.md.

Validation limits

The checked-in tests use deterministic synthetic fixtures. No real physical drive, real deleted volume, labeled accuracy corpus, 24-hour fuzz campaign, or hardware performance target has been validated. Relift is not certified for forensic evidence acquisition; see forensic-use.md and VERIFICATION.md.

Recovery evidence and limits

The Rust suite uses deterministic synthetic FAT32, exFAT, NTFS, and ext4 fixtures with byte-exact SHA-256 verification. Probe detection fixtures were added for HFS+, APFS, Btrfs, and XFS (identified but metadata recovery not implemented). Carving now includes structurally validated FLAC, OLE, MPEG-TS, RAR5, and ISO 9660 in addition to the previous 200+ formats. Tests check source-image immutability, destination separation, path confinement, CLI JSON contracts, exit codes, and Tauri DTO field names. These tests do not measure precision or recall on a representative corpus and do not exercise physical drives.

Gap report

Documented gaps in Relift's current implementation. Each gap is honest, deliberate, and tracked.

Filesystem parsing gaps

NTFS

  • $ATTRIBUTE_LIST: multi-attribute records are not followed; only unnamed $DATA and resident data are recovered.
  • Named alternate data streams: not recovered.
  • Compression (LZ77) and EFS: not decoded; reported as unsupported when encountered.
  • $UsnJrnl: journal not replayed.
  • $I30 directory-index slack and $Recycle.Bin metadata are not parsed as separate sources.

ext2/3/4

  • Inline data larger than the inode body (>60 bytes): not implemented.
  • Encryption: encrypted inodes reported as unverified, not decrypted.
  • bigalloc: filesystem refused as unsupported.
  • Journal replay: not performed; orphan and deleted-inode recovery only.

HFS+, APFS, Btrfs, XFS

  • Parsers are implemented and wired into scan. Deterministic probe fixtures now exist and are covered by end-to-end detection tests (probe_identifies_hfsplus, probe_identifies_apfs, probe_identifies_btrfs, probe_identifies_xfs). Metadata-based deleted-file recovery is not implemented; output is experimental and identified-only.
  • APFS/Btrfs snapshots are not enumerated as separate recovery sources.
  • XFS inode-number reconstruction is approximate for B+tree leaf records.

Carving gaps

  • ZIP64: shares the PK\x03\x04 local-header magic with ZIP and is handled by the existing ZIP validator rather than a separate carver. A dedicated ZIP64 end-of-central-directory validator is not yet implemented.
  • Every emitted carve must pass a structural validator; unvalidated carves are never emitted.

Image format gaps

  • Only raw images are supported. E01/Ex01, AFF4, VHD/VHDX, VMDK, QCOW2 and DMG/UDIF must be converted to raw before scanning.

Platform gaps

  • Windows: raw physical disk enumeration requires elevation. Non-elevated sessions list drive letters only with an honest warning.
  • Windows ARM64: no build or runtime testing yet.
  • macOS: raw-device destination safety fails closed with imaging advice; macOS raw paths are untested.
  • Linux: raw device access may require root. Destination separation resolves partition, stacked-device, and NVMe namespace ancestry through sysfs; virtual destinations whose physical backing cannot be proven are refused. Btrfs destinations are refused because mount metadata does not establish every device in a multi-device filesystem. No io_uring or O_DIRECT path.
  • GUI bundles are unsigned: no Authenticode certificate, Apple Developer ID or notarization credentials are configured.

Validation gaps

  • npm audit (2026-11-15) reports one low-severity prototype-poisoning advisory in the transitive, development-only deepmerge dependency of @sveltejs/vite-plugin-svelte. The upstream advisory lists no patched version; the affected package is not part of the built desktop runtime.
  • Recovery and imaging now walk canonical destination paths from the volume root with no-follow directory opens, retain directory handles, and create output relative to those handles. This blocks traversal through symlinked or replaced destination ancestors after validation. Linux and macOS finalization use no-replace rename; Windows uses a no-overwrite move while destination directory handles remain open. A local process with write access can still modify output data or cause denial of service, and recovery files are visible under their final names while being written.
  • Windows removes failed recovery outputs relative to the open parent handle instead of moving them to .partial; Linux and macOS retain failed outputs under collision-safe .partial names when possible.
  • No real NTFS/ext4 volumes available locally. All validation so far is against deterministic synthetic fixtures (FAT32, exFAT, NTFS, ext4) with SHA-256 byte comparison.
  • Cross-platform CI builds and runs the synthetic test suite on macOS. This Windows development host cannot exercise macOS raw-device behavior, and no raw physical media has been validated on any platform.
  • Public test images or real-volume validation still needed before claiming real-media recovery.
  • cargo-fuzz harnesses for the signature carver and filesystem probes are checked in under fuzz/, and CI runs bounded fuzz executions on Linux runners (nightly + clang). Local Windows execution is blocked because the clang/libFuzzer runtime DLL is not installed on this host; the harnesses compile cleanly. A sustained 24-hour fuzz campaign and crash-minimized corpus remain pending CI execution.
  • Code coverage is not measured in CI.

Interface gaps

  • No TUI. The CLI and Tauri desktop GUI are the supported interfaces.
  • The GUI exposes stop/cancel but not live pause/resume for scans; checkpoint resume is CLI-only via relift scan --resume.
  • The GUI does not export JSON/CSV/HTML reports; use relift report on the session directory.

Release gaps

  • No signing certificates or notarization credentials. Releases are unsigned unless credentials are provided.
  • Homebrew, winget, Scoop, AUR, Flatpak and Snap manifests are not yet submitted to their upstream repositories.
  • Linux ARM64 is cross-compiled for the CLI only; GUI bundles are x86_64.

Deliberate exclusions (not bugs)

  • No simulated or mock results; every fixture-validated recovery is compared byte-for-byte with SHA-256.
  • No faked benchmarks, screenshots, stars, reviews, or release claims.
  • No telemetry; default offline.
  • Unsupported filesystems are identified and reported, never silently claimed.
