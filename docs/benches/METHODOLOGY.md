# Benchmark Methodology

## Purpose

This document describes how Relift's performance and accuracy benchmarks are conducted, so results are reproducible and comparable.

## Test images

### Synthetic fixtures (exact, reproducible)

Generated by `crates/relift-testkit` with fixed seeds. Each fixture has a ground-truth manifest with SHA-256 for every file.

| Image | Size | FS | Files | Deletion scenarios |
|-------|------|----|-------|-------------------|
| `fat32-bench.img` | 1 GB | FAT32 | 10,000 | Normal delete, format, partial overwrite |
| `exfat-bench.img` | 1 GB | exFAT | 10,000 | Normal delete, format, partial overwrite |
| `ntfs-bench.img` | 16 GB | NTFS | 100,000 | Normal delete, recycle bin, shift-del, partial overwrite, MFT fragmentation |
| `ext4-bench.img` | 16 GB | ext4 | 100,000 | Normal delete, journal, orphan, sparse, unwritten |
| `carve-bench.img` | 64 GB | RAW | 5,000 | Mixed formats, fragmented, truncated, nested |

All images committed to `fixtures/` (small) or generated on-demand (large) with `make -C fixtures`.

### Real hardware validation (supplementary)

When available, tests run on:
- Samsung 870 EVO 1 TB (SATA SSD)
- WD Black SN850X 2 TB (NVMe)
- Seagate IronWolf 4 TB (HDD, 7200 RPM)
- SanDisk Extreme Pro 128 GB (SD card)
- Samsung T7 Shield 2 TB (USB 3.2)

Results reported separately; not used for CI gating.

## Benchmark categories

### 1. Signature sweep throughput
**Target**: `benches/signature_sweep`

Measures raw `memchr` multi-pattern search speed on a 64 MB buffer with embedded JPEG/PNG/PDF/ZIP signatures every 1 MB.

**Metric**: MB/s (buffer size / wall time)

### 2. Carver validation throughput
**Target**: `benches/carvers`

Measures `scan_volume` on single-format test files (1 MB JPEG, 1 MB ZIP, etc.).

**Metric**: MB/s (file size / wall time per carver)

### 3. Metadata scan throughput
**Target**: `benches/metadata_scan`

Measures `scan_metadata` on fixture images.

**Metric**: MB/s (image size / wall time), plus recall/precision against ground truth.

### 4. End-to-end deep scan
**Target**: `benches/e2e`

Full `run_scan` with `--mode deep --carve` on `carve-bench.img` (64 GB).

**Metrics**:
- Wall time
- Throughput (GB/s)
- Peak RSS (from `/usr/bin/time -v`)
- CPU utilization (average %)
- Candidates emitted / verified / false positive rate

### 5. Quick scan
**Target**: `benches/quick_scan`

`run_scan` with `--mode quick` on `ntfs-bench.img` (16 GB) and `ext4-bench.img` (16 GB).

**Metrics**: Wall time, throughput, recall/precision.

### 6. Imaging
**Target**: `benches/imaging`

`create_image` on NVMe→NVMe (1 TB), HDD→NVMe (4 TB), bad-sector drive (500 GB).

**Metrics**: Throughput, verified hash match, map file size.

### 7. Recovery
**Target**: `benches/recovery`

`run_recovery` on 1000 JPEGs (2.4 GB) and 500 mixed files (12 GB).

**Metrics**: Throughput, verification pass rate.

## Accuracy measurement

For each fixture with ground truth:

```rust
// Pseudocode
let recovered = relift_recover(session, dest);
let ground_truth = load_fixture_manifest(fixture);

for (path, expected_hash) in ground_truth.deleted_files {
    let recovered_file = dest.join(path);
    if recovered_file.exists() {
        let actual_hash = sha256(&recovered_file);
        if actual_hash == expected_hash {
            true_positive++
        } else {
            false_positive++ // corrupted recovery
        }
    } else {
        false_negative++ // missed
    }
}

recall = true_positive / (true_positive + false_negative)
precision = true_positive / (true_positive + false_positive)
name_accuracy = recovered_with_original_name / true_positive
path_accuracy = recovered_with_original_path / true_positive
```

### CI integration
- Weekly scheduled run on dedicated runner (same hardware class)
- Results uploaded as artifact
- Regression alert if any metric drops >10% from baseline
- Baseline stored in `benches/results/baseline-main.json`

### Publication
Results published to `gh-pages` at `https://relift.rs/benchmarks/` with:
- Interactive charts (Chart.js)
- Raw CSV download
- Hardware + software spec
- Comparison table vs PhotoRec/TestDisk/Recuva (when run)

## Reproducibility checklist

- [ ] Fixed Rust toolchain (`rust-toolchain.toml`)
- [ ] Fixed dependencies (`Cargo.lock` committed)
- [ ] Deterministic fixtures (fixed seeds in testkit)
- [ ] Pinned CI runner (same instance type)
- [ ] CPU governor set to `performance`
- [ ] Swap disabled
- [ ] Thermal throttling monitored (thermal zone < 80°C)
- [ ] Results include full hardware + software spec

## Comparison protocol (vs other tools)

When benchmarking against PhotoRec, TestDisk, Recuva, etc.:

1. **Same hardware**, same images, same mount points
2. **Same goal**: recover deleted files from fixture images
3. **Same metric**: recall/precision against ground truth
4. **Tool versions pinned** in benchmark script
5. **PhotoRec/TestDisk**: run via `photorec /dev/stdin` scripted; `testdisk /log /cmd` scripted
6. **Recuva**: run on Windows VM (same host hardware via PCIe passthrough)
7. **No tuning**: default settings for all tools (Relift defaults vs their defaults)
8. **Report where competitors win** (e.g., PhotoRec format breadth)

## Continuous benchmarking

- **Weekly**: Full suite on dedicated runner
- **On release tag**: Full suite + comparison
- **On PR**: Quick sanity (signature sweep + metadata scan only)
- **Regression threshold**: 10% throughput drop or 1% recall drop → alert

## Historical data

Results archived in `benches/results/YYYY-MM-DD-<commit>.json`. Trend analysis published quarterly.
