## 4. Demo image (original, synthetic, authored by script in this session)

The image was generated by `docs/assets/demo/scripts/genimg.rs` (a standalone
Rust program that does NOT depend on or call Relift code). It builds a raw
FAT32 "superfloppy" image byte-by-byte and writes a boot sector, FAT, root
directory (clusters 2→3), and file data clusters.

- Image: `demo/evidence.img`, 128 MiB FAT32, 512-byte clusters
- Image SHA-256: `0cc2c65aaea9fbb4ded6b240d6171d64f06bba9861a4b29337951fb6d6ad2f33`
  (computed by genimg before any Relift run, and re-verified with
  `Get-FileHash` after recovery — identical, read-only proof below)
- genimg self-check: all 15 files' on-disk bytes == in-memory bytes (the image
  really contains what the manifest claims)
- Files: 15 total, 11 deleted (Windows-style: directory entry first byte 0xE5;
  4 with FAT chain retained, 7 with chain freed), 4 left live as controls
- File formats (all authored by script, no downloaded/stock content): PNG,
  PDF, DOCX, XLSX, ZIP, SQLite, WAV, CSV, TXT. Sizes ~40 KB–2.8 MiB.
- `manifest.sha256` written **before deletion and before any Relift run**.
  Format: `<sha256>  <path>` (one per original file).
- `expected.tsv` records path, hash, deleted, chain_retained, size, first cluster.

The image is small, unfragmented, contiguous, and synthetic. No real drive,
no personal data, no real user files.

**Unmatched recovered (74) — carved SQLite candidates:**

All 74 are `carved_....sqlite`. Exactly ONE of them is the real

carves: my synthetic SQLite writes a valid "SQLite format 3" header at the
start of *every* 4 KiB page, so Relift's validator accepts each page as a
candidate. This is a known carving artifact of this particular synthetic
fixture, not a Relift defect. A real file rarely has a valid header on every
page.

Summary: matched=11, not-recovered-controls=4, extra_recovered=74.
Deleted files recovered byte-for-byte: **11 of 11 (100%)**.

## 12. Statement of limits

- All recovery evidence comes from deterministic synthetic fixtures (this
  session's genimg image). No real disk image, physical drive, or representative
  recovery corpus was validated — consistent with the project's stated v0.1.0
  preview status.
- No physical device was scanned, imaged, mounted, formatted, or written to.
- No real-media accuracy, speed, or tool-comparison claims are made (none are
  published by the project).
- MCP server, TUI, self-update, `relift info|verify|session`, config files,
  non-raw image formats, and code signing are NOT implemented and not shown.
- HFS+/APFS/Btrfs/XFS are experimental; not showcased.
- The 4 pre-existing `docs/assets/screenshots/*.png` files are placeholders
  (a VS Code window, not the Relift GUI) and were NOT used or replaced here.
